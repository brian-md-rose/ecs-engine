# The editor overlay

`engine::editor` is a [Dear ImGui](https://github.com/ocornut/imgui) editor for the engine. It is an overlay drawn on top of a running game (the hook and shell, Hierarchy and Inspector panels), and also the standalone editor with scene files, Play and Stop, a Viewport and undo and redo, all described below. It is off by default, so a game that doesn't want it never compiles it and `engine::platform` doesn't depend on it.

## Building it

```
git submodule update --init thirdparty/imgui
cmake -S . -B build/editor -DENGINE_BUILD_EDITOR=ON
```

That adds `engine::editor`, the `tangle_run_editor` executable (Tangle Run with the overlay) and, with tests on, `editor_tests`. CI builds it on Windows (MSVC) only. The code is plain SDL3 and ImGui, and was also built with GCC and Clang during development, but nothing checks that.

## Using it

In `tangle_run_editor`, F1 (which the game never sees) shows and hides the overlay. While it is shown, a menu bar appears with **Panels** (Hierarchy, Inspector and the ImGui demo window) and **Help > About**. The mouse and keyboard go to the overlay's windows when the pointer is over one or a text box has focus, and to the game otherwise. The system mouse pointer is shown while the overlay is, even when the game draws its own.

## Assets

The **Assets** panel (Panels menu) lists what is under the game's assets folder (the source folder next to `scenes/`): **Sprites** (every `sprite` of a `.sheet` manifest, and the `region`s of one that is not a font), **Fonts** (a `.sheet` made only of single-character regions, named by its file) and **Sounds** (`.ogg`, `.wav`, `.flac` and `.mp3` files, named by their path inside the folder, like `music/theme.ogg`). Each tab shows a name and details (size and frames, glyph count, format); hovering shows the file. The search box filters by name, *Copy name* puts the selected name on the clipboard, and *Rescan* looks at the folder again after files change. The Sprite component's `source` (a rectangle in the atlas) also has a **picture** pick-list of the sprite names the game can draw: picking one writes that sprite's rectangle (saved in the scene as the same `x`, `y`, `width` and `height` as before), and the list shows the name the rectangle matches, or *(custom rectangle)*. The game provides the name-to-rectangle lookup (`EditorGameConfig::spriteRect`). The Inspector's pick-lists read the same catalog (`PanelState::assets`), so a new sprite in a sheet shows up in the `ClipName` list after Rescan. Text sheets (`.txt`) are the game's fallback and are not listed. A game gives the folder with `EditorGameConfig::assetFolder` (or `AddAssetBrowser` in overlay mode) and marks its fields with `FieldHints::assetKind`. **Thumbnails and import settings:** the Sprites tab has a *Grid* checkbox (and a size slider) that shows each sprite's first frame as a picture instead of the list. Selecting a sprite shows it in a preview beside the list (the whole strip, yellow lines between frames) and its **Import settings**: cell width, cell height and frames, plus x and y for a `region`. *Apply* rewrites that sprite's line in the `.sheet` (name and PNG stay, other lines are untouched) and is refused, with the reason shown, if the manifest would no longer load, for example a cell size that does not fit the PNG; *Revert* drops the edit. Pictures need the standalone editor; the overlay editor shows the settings without a picture. Filter mode and pivot are not settings, since the manifest format has no such fields. **Drag and drop:** every row (sprite, font, sound and, in the **Scenes** tab, a scene file) can be dragged. Dropping a sprite on the Viewport (edit mode) adds an entity with Name, Transform and Sprite centred on the pointer (on the grid when Snap is on; Ctrl flips it) and selects it; dropping a sprite on a Sprite `source`, or a font, sound or sprite name on a field with that asset kind, sets it, as picking from the list does; dropping a scene on the Viewport opens it, asking first if there are unsaved changes. Each drop is one undo step.

## Console

The **Console** panel (Panels menu, docked at the bottom by default) shows what the game and the engine log through `core::Log`, oldest first, coloured by level. The level buttons (with a count each) hide or show Debug, Info, Warn and Error; the filter box keeps the messages that contain the text, ignoring case. *Clear* forgets the messages, *Copy* puts the lines shown on the clipboard, and right-clicking a line offers *Copy line*. With *Auto-scroll* on, the view follows new messages until you scroll up. The panel keeps the last 2000 messages (`AddConsolePanel(editor, capacity)`); while a log session is running, anything below its minimum level (Info unless the game's `LogConfig` says otherwise) is never recorded. The standalone editor adds it itself; an overlay game calls `AddConsolePanel`. Any other viewer can read `core::LogHistory()`.

## Build settings

The **Build settings** panel (Panels menu, standalone editor, Windows) packages the game. Tick the scenes that ship (a new setup ticks all of them), click one to make it the **startup** scene, and set the *Game exe* (by default `game.exe` beside the editor) and the *Output folder* (by default `package/Tangle Run` beside the editor). **Package** writes the executable, a copy of `assets/` without the scenes you left out, and `build.json`, a manifest with the game name, engine version, startup scene, scene names and every file of the package. Only the package's own `assets/` is replaced; the panel refuses an output folder that would overwrite the source assets or the executable. **Package and run** also starts the packaged game. The choices are kept in `editor-build.json` beside the editor log. The game does not read the startup scene yet: Tangle Run still starts on its own first screen, so the manifest is a record for now. A game uses `AddBuildSettingsPanel(editor, config)`.

## Profiler

The **Profiler** panel (Panels menu) plots the frame time of the last 240 frames, with a second graph for the share spent in the game's Update (only while Play runs), and shows the FPS, average and worst frame time and the entity count. The table lists how many entities have each component in the world being shown (the played one while playing), biggest first; *Hide empty* drops components nobody has. *Pause* freezes the graph, *Clear* empties it. Frames are recorded only while the panel is open. "Other" is everything that is not Update: drawing, the editor UI and waiting for vsync. An overlay game calls `AddProfilerPanel(editor, worldFunction)`; the standalone editor adds it itself. There are no per-system timings yet.

## Hierarchy and Inspector

`AddEntityPanels(editor, world)` (`editor/entitypanels.hpp`) adds both panels for a `ecs::World`. The world needs a `TypeRegistry` resource with the components registered (see [scenes](scenes.md)); only registered components are shown.

- **Hierarchy:** every entity as a tree by `Parent`, labelled by its `Name` (or `Entity <index>`), with a filter box. Click selects; Ctrl or Shift click adds an entity to the selection (or takes it out), and Duplicate, Delete and the Viewport's moves act on all of it. The Inspector shows the first one picked, and edits what it shows on every selected entity (below). Drag an entity onto another to make it a child, or onto the "top level" line to unparent it; a move that would make an entity its own ancestor is refused. Right-click for *Add child*, *Duplicate* (the entity and everything under it, with references between them pointing at the copies) and *Delete* (with everything under it). *New entity* makes one at the top level.
- **Editing several entities:** with more than one entity selected, the Inspector lists the components of the primary one. Changing a field writes the new value to every selected entity that has that component, as one undo step. A field whose values differ across them shows `-` (numbers) or an orange tint (anything else), with a tooltip; touching it sets them all to the value you pick. Removing a component, or adding one from *Add component*, also applies to the whole selection. A Parent change that would make a loop is skipped for that entity and reported in the status line. *Copy values* and *Paste values* still use the primary entity only.
- **Inspector:** the selected entity's registered components, each in a collapsible section (the close button removes the component), and *Add component* for the ones it lacks. Fields are widgets by their registered kind: checkbox, drag or slider (using the field's min and max hints), text, combo for enums, an entity picker for entity references and lists, and a generic number editor for custom types such as a `Color`. A text field registered with `FieldHints::assetKind` (`ClipName` is a `Sprite`) is a list of the sprites, fonts or sounds the **Assets** panel finds, and one with `FieldHints::choices` is a list of those values; either way it is a list to pick from instead of a text box; a value that is not in the list is shown marked and kept until another is picked. Components marked Runtime are hidden. Read-only fields are greyed out and a field's tooltip shows on hover. The **Scene** panel edits the scene's settings (camera position and zoom, background colour; see [scenes](scenes.md)); they are saved with the scene, count as changes for undo and the unsaved mark, and Play uses them. The search box above the components shows only those whose name (or a field's name) contains the text, ignoring case. Right-click a component's header for *Copy values* and *Paste values*: the values go to the clipboard as JSON, and pasting onto another entity's header of the same component (adding the component if it lacks it) sets every field in the text; if a field does not load, nothing changes.

The panels change the registry directly, between frames: the editor draws after the game's update and render, so no system is running over the entities. They go through `Registry::Add` and `Destroy`, so `OnAdd` and `OnRemove` hooks still run. A change the game's systems keep overwriting (a position they set every update) will not stick. The operations behind the panels (`editor/entityops.hpp`: `CreateEntity`, `SetParent`, `DestroyTree`, `DuplicateTree`) are plain functions on a `Registry` and are unit tested.

To add the editor to another game:

```cpp
engine::editor::Editor editor;
editor.AddPanel("My panel", [] { ImGui::Text("hello"); });
app.SetEditorHost(&editor);
app.Run(game);
```

and link `engine::editor`. A panel is any function that calls ImGui; it gets its own window, opened from the Panels menu.

Panels dock (Dear ImGui's docking branch): drag a panel by its title into a screen edge or onto another panel to tab it. `Editor::SetPanelDock(name, DockArea)` says where a panel starts in the default layout (Left, Right, Bottom, Center; none leaves it floating); the default is built when the layout file has no dock data, and **Panels > Reset layout** rebuilds it. The middle of the dock space is see-through, so in overlay mode the game still shows there and takes the mouse.

## The standalone editor

`tangle_run_editor` starts as a standalone editor (`--overlay` gives the F1 overlay on the running game instead). `EditorGame` (`editor/editorgame.hpp`) is the `Game` it runs. It holds two copies of the game, both made by `EditorGameConfig::makeGame`:

- The **edit world** has the game's resources and systems but runs none of them. It holds the scene being edited, and the Hierarchy and Inspector work on it.
- The **play world** exists only between Play and Stop. Play saves the edit world's entities, makes a fresh game, loads them into it and runs it. Stop throws it away, so nothing done while playing reaches the scene.

The **Scene** menu has New, Open (the `.json` files in `sceneFolder`; Tangle Run's editor uses the source folder `game/assets/scenes`, so saves are committed with the repository, and falls back to `assets/scenes` next to the executable if that folder is missing), Open recent (the last eight scenes opened or saved), Save and Save as. A `*` beside the name marks changes not saved; New and Open ask before discarding them. Open reads the file first and keeps the current scene if it has errors. `makeGame` must not let a game write the player's save file (Tangle Run's factory clears `SaveFile::path`), since games are made and discarded freely. `afterLoad` runs after each load, for what a game does with its entities after loading (Tangle Run resolves sprite clip names).

If the game asks to quit while it is played (its own Quit), Play stops and the menu bar says so, rather than the run just ending.

**Autosave:** with `EditorGameConfig::autosaveFolder` set, the editor writes the scene there every `autosaveSeconds` (60) while it has unsaved changes, one file per scene (`_untitled_.json` for a new one). Saving, New, or opening another scene deletes the autosave. When a scene is opened and its autosave is newer than the file, a dialog offers to restore it (the restored scene still shows as unsaved) or throw it away. Tangle Run's editor keeps autosaves in `autosave` next to its log, outside the scene folder, so they are never committed by accident.

The **Issues** panel lists every problem the last open, save or Play start reported (errors first, then warnings, each with its JSON path such as `entities[3].components.Follow.target`), where the menu bar only has room for the first; it opens by itself when there is something to list, and New or Clear empties it. An unknown component name in a file is a warning, so a scene survives a removed component, and the panel is where you see which.

The editor remembers the last scene and the panel layout between runs: `EditorGameConfig::recentFile` names a text file of scene names, newest first, and the editor reopens the first one at start (if it is gone you get a new scene and no complaint); `Editor::SetLayoutFile` is where Dear ImGui keeps the panels' positions and sizes. Tangle Run's editor keeps both next to its log (`editor-recent.txt` and `editor-layout.ini` in the save folder). `EditorGameConfig::openOnStart` opens a named scene instead of the last one; `tangle_run_editor title.json` (or `title`) passes its first argument that is not a flag, using only the file name, so it must be in the scene folder. A scene that can't be opened is reported in the menu bar and the editor starts on a new scene.

Saved scenes go to the source folder, and each game the editor makes (the edit world, and the copy for each Play) reads its scene files from that folder again, so an edited screen scene (title, pause and so on) shows in Play straight away. The game itself still reads the copy next to the executable.

`EditorGameConfig::onPlay` is called on the play world after the scene is loaded, so a game can start itself on what the scene holds; Tangle Run uses it to start on its maze when the scene is a maze scene (`level1.json`, see [maze format](maze-format.md#maze-scenes)): the game plays on the scene's tiles instead of spawning its own. Otherwise Play runs the game's own systems over the scene's entities, and a game that also spawns entities when a state is entered does that on top of the scene. Tangle Run's menu screens are scene files that their enter systems load with `SpawnScene`, and its playing field (maze, pellets, enemies, HUD) is still built from code. Play is most useful for scenes the game loads whole, such as `uidemo.json`.

## The viewport

In the standalone editor the game is drawn into a picture (a render target as big as the game's logical screen, `Renderer::CreateRenderTarget` and `SetRenderTarget`) and the **Viewport** panel shows it. The mouse wheel zooms about the pointer, middle or right drag pans, and Reset view puts it back; this moves the view of the picture, not the game's own `Camera`. A click selects the entity drawn under it (Ctrl or Shift click adds to the selection or removes from it, and a press on empty space drags a box that selects what it covers; dragging any selected entity moves the whole selection, and Delete, Ctrl+D and the arrow keys act on all of it) (`PickEntity` in `editor/viewport.hpp`: the highest layer, then the later entity), and the selected entity has a yellow outline. Things with a `Shape`, a `Sprite`, a UI `Hitbox`, a `NinePatch` or a `Text` can be picked. A text's size is measured with the engine's default font metrics (6 by 8 pixels a character), so it is exact for the game's own font. Selecting an entity from the Hierarchy scrolls the view to it if it is off-screen. World-space entities go through the game's camera (`Renderer2D::camera`), and `ScreenSpace` ones, or their children, do not. If a renderer can't make a render target, the game is drawn straight to the window instead and the Viewport panel stays empty.

**Play from here:** right-click a cell in the Viewport while a maze scene is open and choose *Play from here*; the game starts with the player on that cell (not on a wall, door, tunnel or enemy start), and Restart (F6) starts there again. A plain Play (F5) starts at the scene's own player start. A game offers it through `EditorGameConfig::onPlayFrom`.

**Translate gizmo:** the selection has a gizmo at the middle of what is drawn (the mean of the middles of the selected entities' outlines, or of just the topmost ones when a parent and its child are both selected): a red arrow to the right (X), a green arrow down (Y) and a square at the pivot. Dragging an arrow moves the selection along that axis only, and the other axis stays exactly as it was (even with Snap on); dragging the square moves it freely. Snap, Ctrl (flips Snap) and Shift (one axis, on the square) work as for any drag. The gizmo is the same size at any zoom, the handle under the pointer lights up, and a drag is one undo step. Dragging the entity itself still moves it, as before. A child of a parent that is turned or stretched moves along the parent's axes (its `LocalTransform` position is in them), so it still follows the pointer.

**Rotate and scale gizmos:** the **Move / Rotate / Scale** buttons above the Viewport (or **W / E / R** with the Viewport focused) choose which gizmo the selection has. *Rotate* is a ring round the pivot: drag it and every selected entity turns by how far the pointer goes round the pivot, each about its own centre (the engine's rotation is about the centre of a Shape or Sprite), with a tick on the ring and the angle shown while dragging. *Scale* has the arrows turned to the entity the Inspector shows, each ending in a square: dragging an arrow multiplies that axis's scale on every selected entity by 1 + (the pointer's travel along the arrow) / (the arrow's length), and the square at the pivot scales both axes (right or up grows, left or down shrinks). Snap rounds a rotation to 15 degrees and a scale to 0.25 (Ctrl flips it); a scale never gets closer to 0 than 0.01, and dragging past 0 mirrors it. A child changes its `LocalTransform` rotation and scale, which add and multiply with its parent's. A drag is one undo step.

**Game extensions (C++ only, no scripting language):** in the explicit registration block of its editor's `main`, a game can fill `EditorGameConfig::inspectors`, `componentCommands`, `entityCommands` and `menu` (the overlay editor sets the same fields on the `PanelState` that `AddEntityPanels` returns). *inspectors* maps a registered component name to a function `(Registry&, Entity)` that draws that component's body with ImGui instead of the field widgets (the header, its close button and its right-click menu stay); it gets the primary selected entity only, so it does not take part in multi-edit. *componentCommands* adds labelled items to the right-click menu of a component's header, and *entityCommands* to an entity's right-click menu in the Hierarchy; each runs `(Registry&, Entity)` once the panel has finished drawing, so it may add, remove or destroy things. *menu* is called inside the menu bar, after Edit, while editing, with the edit world, and draws its own `ImGui::BeginMenu` and `MenuItem`s. Whatever they change is an ordinary scene change (undo, the unsaved mark). For example `config.entityCommands.push_back({"", "Select children", [](Registry& registry, Entity entity) { ... }});` or `config.inspectors["Health"] = [](Registry& registry, Entity entity) { auto& health = *registry.TryGetComponent<Health>(entity); ImGui::SliderInt("hp", &health.value, 0, health.max); };`.

**Scene and Game side by side:** the **Game** panel (Panels menu; drag its tab beside the Viewport) shows the playing game in a picture of its own, with the mouse and keys going to the game while the pointer is over it or it has focus (hold Ctrl to zoom and pan its view). While it is shown during Play, the Viewport does not switch to the running copy: it keeps the scene being edited, so selecting, the gizmos, the grid tool, the Hierarchy and Inspector, Undo and Save all work on the scene while the game runs. Edits made then are in the edit scene only and do not reach the run in progress; Restart (F6) starts again from them. Closing or hiding the Game panel puts Play back as before, one picture in the Viewport. The Viewport's strip also has **Gizmos** (hide the gizmo) and **Grid lines** (a line at every grid size over the scene) toggles. There is still no edit-mode player preview and no way to keep a change made to the running copy.

**Prefabs:** *Edit > Prefab > Save selection as prefab...* saves the primary selected entity and everything under it as `<name>.json` in the assets folder's `prefabs` folder (the same text as *Copy*; a name has no dots, slashes, colons or other characters Windows does not allow in a file name, and the tree may not refer to entities outside it), and puts a `PrefabInstance` component with the prefab's name on the root. The **Prefabs** tab of the Assets panel lists them; drag one onto the Viewport to put a copy of the whole tree there (the root lands on the pointer, on the grid with Snap), selected, with the same undo step as any edit. A copy is ordinary entities that remember their prefab through `PrefabInstance` on the root: *Edit > Prefab > Apply to prefab* saves the copy over the prefab file (other copies already in scenes keep what they have until reverted or placed again), and *Revert to prefab* replaces the copy's tree with a fresh one from the file, keeping its parent and position. There are no per-instance overrides or nested prefabs yet, and the Prefabs folder is under the assets folder, so Build settings packages it with the game.

**Picking follows rotation and scale:** clicking, the box select and the selection outline use the turned and stretched outline of a Shape or Sprite, not the box it had before. Text, nine-patches and UI hitboxes are not turned by the renderer, so they keep their plain box.

While playing, the game also gets the keyboard (arrow keys, P and so on) whenever the pointer is over the Viewport or it has focus, unless a text box wants the keys; ImGui keyboard navigation is off then (`Editor::SetGameKeys`). F5 and F6 still work. The game gets the mouse over the viewport (`PlayMouse`, `editor/viewport.hpp`): positions are in the picture's pixels, a press that began over the viewport stays with the game until it is released, and the wheel and buttons go to the game, so hold Ctrl to zoom and pan the view instead. Clicking and dragging do not select or move entities while playing. Dragging an entity in the viewport moves it. **Snap** (next to Reset view) rounds the result to multiples of the grid size beside it; holding Ctrl while dragging flips the setting, and holding Shift keeps only the larger of the two movements. The arrow keys nudge the selection one unit, or one grid step with Shift (only while the Viewport has the pointer or focus, and not while typing in a text box; with Snap on a nudge is one grid step and lands on the grid). What moves is its `LocalTransform` if it has a parent, otherwise its `Transform`, scaled by the camera zoom for world-space entities.

## Undo and redo

**Edit > Undo** (Ctrl+Z) and **Redo** (Ctrl+Y, or Ctrl+Shift+Z) step through the changes made to the scene, up to 100, in the standalone editor. A step is a finished change: a whole drag in the viewport, a value typed into the Inspector until the box is left, one menu click (add child, duplicate, delete, add or remove a component). It is found by looking at the scene when the pointer and widgets go quiet, so everything the editor can change is covered, with no changes needed in the panels. New and Open start the list again, and there is no undo while playing. A text box being typed in keeps its own Ctrl+Z.

This differs from the plan's per-component commands: each step is the whole scene as text (`SaveScene`), and undoing loads the neighbouring one. It is simple and covers creating and deleting entities too, at the cost of memory for large scenes and of entity ids changing on each undo (the selection is kept by its position in the scene).

## How it hooks in

`application/editorhost.hpp` defines `EditorHost`, with no SDL types (the window, renderer and events cross as opaque pointers). `Application::SetEditorHost` takes one, not owned, and then:

- calls `Attach` just before the main loop and `Detach` after it;
- passes every SDL event to `OnEvent` first, and skips the game's own handling when it returns true (a close request is never taken);
- calls `Draw` after the game's `Render` and before the frame is presented;
- asks `WantsSystemCursor` each frame.

With no host set, none of this costs anything. The overlay draws at real window pixels, not the game's logical size, so its text stays sharp: `Editor::Draw` turns the renderer's logical presentation off for the overlay's draw calls and back on after. It writes no `imgui.ini`.

ImGui is a submodule pinned to a release tag of the docking branch (v1.92.9b-docking); to update it, check out another tag in `thirdparty/imgui` and commit.

## Shortcuts

In the standalone editor: Ctrl+S Save, Ctrl+Shift+S Save as, Ctrl+N New, Ctrl+Z Undo, Ctrl+Y (or Ctrl+Shift+Z) Redo, Ctrl+C copy and Ctrl+V paste the selected entities (each with what is under it, as scene text on the clipboard, so a paste can go into another scene or be saved in a text file; it fails with a message if a copied entity refers to one that was not copied), Ctrl+D duplicate the selected entity, Delete delete it and everything under it, F5 Play or Stop, F6 Restart (stops and plays again from the edit world as it is), F7 Pause or Resume Play, F8 Step (one 1/60 s update while paused). While playing only F5 to F8 work. The Play menu items also have Speed (0.25x to 4x) and Mute (the game gets no audio device). None of them act while a text box has focus, a drag is in progress or a dialog is open.

## Painting a grid scene

A game can give the standalone editor a `GridTool` (`editor/gridtool.hpp`, through `EditorGameConfig::gridTool`): a palette of tile kinds and functions to paint and erase a cell. When the scene being edited has a grid (Tangle Run's maze scenes, `game/assets/scenes/level1.json`), the Viewport shows a row of radio buttons: **Select** (the usual click and drag), one for each palette entry (Wall, Door, Pellet, Power pellet, Player start, Enemy start, Tunnel) and **Erase**. With a brush chosen, the grid is drawn over the picture, the cell under the pointer is outlined, and pressing and dragging with the left button paints every cell the pointer crosses (`CellLine`, so a fast drag leaves no gaps). Painting a cell replaces what is in it, painting what is already there changes nothing, and a maze has one player start, so painting a second moves it. After each frame that painted, the game's `refresh` runs (for the maze it places the tiles and joins the walls up again). A whole stroke is one undo step. **Shapes:** with a palette entry or Erase chosen, a second row picks how a drag lands: **Freehand** (as above), **Line**, **Rectangle** (outline) and **Filled** (press at one corner and drag to the other; the cells are outlined while dragging and are painted when the button comes up over the grid, leaving the pointer outside the grid cancels), and **Fill**, which paints the connected cells (side to side, not corners) that hold the same thing as the clicked one, so it fills an empty area or turns a run of pellets into another tile. **Copy and Stamp:** *Copy* drags a rectangle of cells and keeps what they hold (empty cells too) as a stamp, then switches to *Stamp*, where the stamp follows the pointer (top-left on the cell under it, clipped at the grid's edge) and a click puts it down, replacing the cells under it. Each is one undo step. Fill, Copy and Stamp need the game's `GridTool::kindAt` (what a cell holds); Tangle Run gives it (`MazeTileKindAt`). What is wrong with the maze as it stands (no player start, a tunnel without its pair) is shown in orange above the picture, and Play refuses to start on a maze that isn't valid, saying why in the menu bar.

The grid is laid over the picture at the game's own pixels, so it is right for a game whose camera is at its default (Tangle Run's is). The brush is off while playing.

**Known limits** (things that behave in a way you might not expect): a component's custom Inspector widget (`EditorGameConfig::inspectors`) replaces the field widgets, so the Inspector's field search does not filter inside it; only one component command runs per frame; *Revert to prefab* replaces the copy's tree with new entities, so references to the old ones from outside the tree are left dangling; prefab names are checked against the characters Windows forbids, but not against its reserved device names (`CON`, `NUL` and so on); and the grid tool's `kindAt` is searched per cell, so Fill on a very large grid is slow.
